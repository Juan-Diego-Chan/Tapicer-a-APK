# Plan 4: Dinero — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Empleados y dueño registran pagos de clientes (anticipo, abonos, liquidación), y el pedido muestra su saldo. El dueño registra devoluciones y corrige pagos. Cada empleado ve el dinero que tiene en sus manos y registra entregas; el dueño las confirma o rechaza y ve lo que tiene cada quien. El dueño registra los pagos de sueldo. Además, agregar o cancelar un mueble queda en el historial de precios.

**Architecture:**
- Modelo y cálculos puros en `dominio/dinero.dart`.
- Dos contadores, actualizados con `FieldValue.increment` en el mismo lote que el pago o la entrega:
  - `pedidos/{p}.pagado`: Σ pagos del pedido.
  - `cajas/{uid}.enMano`: Σ cobros del empleado − Σ entregas confirmadas.
- Las reglas verifican cada contador con `get`/`getAfter` en las dos direcciones, igual que `cambios_precio` en el Plan 3. Con los contadores:
  - el empleado ve el saldo de cualquier pedido sin leer los cobros de otros (§5: solo el dueño ve "cuánto cobró cada trabajador");
  - ninguna pantalla lee todos los pagos (cuotas de Spark).
- Escrituras en `ServicioDinero`. Las altas y cancelaciones de muebles se agregan en `ServicioPedidos`.
- Pantallas:
  - sección "Pagos" en la pantalla del pedido;
  - anticipo en "Nuevo pedido";
  - pantalla `/dinero` para empleado y dueño;
  - pantalla de sueldos `/usuarios/:uid`, solo dueño.

**Tech Stack:** igual que el Plan 3 (Flutter 3.47, Riverpod 3, go_router, cloud_firestore, fake_cloud_firestore; reglas con vitest y el emulador). No se agregan dependencias.

**Spec:** `docs/superpowers/specs/2026-11-04-app-tapiceria-design.md`. Secciones que aplica: §5, §6.1 ("ningún cambio de precio pasa sin quedar registrado"), §6.6 (pago de sueldos), §6.7, §6.7.1 y §6.8 (devoluciones). **Hoja de ruta:** `docs/superpowers/plans/2026-11-04-00-hoja-de-ruta.md`. ## Cambios al modelo de datos

| Colección | Campos | Notas |
|---|---|---|
| `pedidos/{id}` | + `pagado` (num ≥ 0), + `ultimoPagoId?` | Si `pagado` falta, se lee como 0 (pedidos del Plan 3). |
| `pagos/{id}` | `pedidoId`, `monto` (≠ 0; negativo = devolución), `forma` (`'efectivo'`\|`'transferencia'`), `recibidoPor`, `fecha` | Igual que la hoja de ruta. Inmutable; solo el dueño lo borra. |
| `cajas/{uid}` (nueva) | `enMano` (num), `ultimoPagoId?`, `ultimaEntregaId?` | Solo para empleados. La lee el dueño y el propio empleado. |
| `entregas/{id}` | `empleadoId`, `monto`, `forma`, `fecha`, `estado` (`'pendiente'`\|`'confirmada'`\|`'rechazada'`), `revisadoEn?` | Igual que la hoja de ruta. Nadie la borra. |
| 🔒 `pagos_sueldo/{id}` | `usuarioId`, `monto`, `fecha` | Igual que la hoja de ruta. |
| `pedidos/{p}/cambios_precio/{id}` | `campo` gana `'alta'` y `'cancelacion'` | Alta: `anterior` 0 y `nuevo` = precio. Cancelación: `anterior` = precio y `nuevo` 0. |

## Global Constraints

### Firebase
- **Plan Spark únicamente.** Nada de Cloud Functions, Cloud Storage ni nada que pida Blaze.

### Escrituras
- **Sin conexión primero.** Toda operación es un solo `WriteBatch`, **sin transacciones** y sin `get()` previo dentro del servicio. Los datos actuales (pedido, caja, entrega) llegan como parámetros desde la pantalla.
- La UI **no espera** `commit()`. Lanza el commit y cierra o navega de inmediato. Si falla, muestra el SnackBar "No se pudo guardar", guardando antes el `ScaffoldMessenger`. Usa `guardarSinEsperar` de `dialogos_pedido.dart`, ya existe.
- Los contadores `pagado` y `enMano` **solo** cambian con `FieldValue.increment`, nunca con un valor absoluto. Así dos teléfonos sin conexión que cobran el mismo pedido suman los dos pagos.
- `fecha` de pagos y entregas y `revisadoEn` de entregas usan `FieldValue.serverTimestamp()`, y las reglas exigen `== request.time`. Mientras el registro está pendiente, la app muestra la hora local, igual que `cambios_precio`.
- `pagos_sueldo.fecha` la elige el dueño; puede ser cualquier fecha.

### Comparar dinero en reglas
- Los incrementos de punto flotante dejan residuos (0.1 + 0.2 ≠ 0.3). Toda igualdad de **deltas** de contador usa `igualDinero(a, b)`, que es `math.abs(a - b) < 0.001`. Las comparaciones de campos copiados (precio, anterior, nuevo) siguen siendo `==`.

### Visibilidad
- El empleado **nunca** lee pagos que no recibió él, cajas ajenas, entregas ajenas ni `pagos_sueldo`.
- En la pantalla del pedido, el empleado ve los totales (total, pagado y saldo) y **solo sus propios cobros**; el dueño ve la lista completa. Ninguna pantalla del empleado se suscribe a providers que solo puede leer el dueño.

### Inmutables
- Los pagos no se editan. **Solo el dueño** los borra: el borrado descuenta `pagado` y, si lo cobró un empleado, `enMano`. Para corregir un pago, se borra y se registra de nuevo.
- Las entregas no se editan ni se borran. Solo pasan de `pendiente` a `confirmada` o `rechazada`, una sola vez y solo por el dueño.
- **Cancelado es definitivo:**
  - un mueble cancelado no vuelve a otro estado;
  - el dueño solo puede borrar muebles cancelados;
  - un pedido con `pagado ≠ 0` no se puede borrar.

### Valores exactos
- Forma de pago: `efectivo` → "Efectivo", `transferencia` → "Transferencia".
- Estado de entrega: `pendiente` → "Pendiente", `confirmada` → "Confirmada", `rechazada` → "Rechazada".
- **Saldo del pedido** = total − pagado, con `redondear2`. El total sale de `totalPedido` del Plan 3.
- **Dinero en manos** = `cajas/{uid}.enMano`, o 0 si la caja no existe.
- **Por entregar** = en manos − Σ entregas pendientes del empleado.
- Solo un **empleado** escribe en su caja al cobrar. Los cobros del dueño no tocan ninguna caja (§6.7.1).
- Un pago positivo va de 0.01 a 999,999,999.99. Una devolución es un pago negativo y solo la registra el dueño.

### Formato
- Textos en español (México).
- Dinero: `formatearDinero` para mostrar y `leerDinero` para leer; "1,500" se lee como 1500.
- Fechas: `formatearFecha`.
- Una devolución se muestra como `-$200.00`, en el color `colorScheme.error`.

### Consultas
Todas acotadas:

| Consulta | Filtros y orden | Índice |
|---|---|---|
| Pagos de un pedido (dueño) | `pedidoId == p`, ordenados en memoria por fecha | No necesita |
| Pagos de un pedido (empleado) | `pedidoId == p` y `recibidoPor == uid` | No necesita: son igualdades |
| Entregas pendientes (dueño) | `estado == 'pendiente'` | No necesita |
| Entregas de un empleado | `empleadoId == uid`, orden `fecha` descendente, límite 30 | `(empleadoId ASC, fecha DESC)` |
| Pagos de sueldo de un usuario | `usuarioId == uid`, orden `fecha` descendente, límite 20 | `(usuarioId ASC, fecha DESC)` |
| Cajas (dueño) | La colección completa (una por empleado) | No necesita |

### Prácticas heredadas
- Los repositorios **omiten** documentos mal formados.
- Las reglas validan forma con `hasOnly` y tipos, y rechazan NaN e Infinity.
- En las pantallas, importa el dominio con `hide Material`.

## Review Focus

1. **Anticipo sin conexión.** Un empleado en modo avión crea un pedido con un anticipo de $500 en efectivo, y la pantalla navega de inmediato. Al sincronizar, el pedido tiene `pagado` 500 y la caja del empleado `enMano` 500. Si dos teléfonos cobran el mismo pedido en lotes separados, `pagado` suma los dos. → Tareas 3 y 7.
2. **Montos mal escritos.**
   - "1,500" se lee como 1500.
   - "0", "-5" y "abc" se rechazan con mensaje.
   - Un pago mayor que el saldo muestra "El pago es mayor que el saldo ($X)".
   - Una devolución mayor que lo pagado se rechaza.
   - Una entrega mayor que lo que hay por entregar se rechaza.
   - → Tareas 6, 8 y 9.
3. **Empleado tramposo contra Firestore directo.** Falla todo esto:
   - leer pagos ajenos, la caja de otro o entregas ajenas;
   - subir su caja o el `pagado` sin un pago;
   - registrar una devolución, borrar un pago o confirmar su propia entrega;
   - crear un pago a nombre de otro;
   - reactivar un mueble cancelado.
   - → Tareas 2, 3 y 4.
4. **Residuos de punto flotante.** Pagos de $0.10 y $0.20, y luego borrar el de $0.10. Las reglas aceptan las tres escrituras y el saldo muestra la cuenta exacta. → Tareas 1 y 3.
5. **Cancelaciones y dinero.**
   - Cancelar un mueble deja "Mueble cancelado: $600.00 → $0.00" en rojo en el historial.
   - Un pedido cancelado no ofrece "Registrar pago", pero sí "Devolución".
   - Si el pedido cancelado tiene pagos, muestra "Anticipo retenido: $X".
   - → Tareas 2, 5 y 8.

### Task 3: Reglas — pagos, saldo del pedido y cajas

**Files:**
- Modify: `firebase/firestore.rules`:
  - `pedidoValido` acepta `pagado` y `ultimoPagoId`;
  - cambian el `create`, el `update` y el `delete` del pedido;
  - se agregan `match /pagos/{id}` y `match /cajas/{uid}`.
- Test: `firebase/pruebas_reglas/pagos.test.ts`, nuevo.

**Interfaces:**
- Produces los lotes que escribe `ServicioDinero` en la Tarea 6:
  - **Cobro de un empleado:**
    - `pagos/{id}` con `fecha: serverTimestamp()` y `recibidoPor` igual al empleado;
    - `pedidos/{p}` con `pagado: increment(monto)` y `ultimoPagoId: id`;
    - `cajas/{uid}`, con `set(merge)` de `enMano: increment(monto)` y `ultimoPagoId: id`.
  - **Cobro del dueño o devolución:** el mismo lote sin la caja. En una devolución, `monto` es negativo.
  - **Pedido con anticipo:** el pedido se crea con `pagado: monto` y `ultimoPagoId: id`, en el mismo lote que el pago y la caja.
  - **Borrado de un pago (dueño):**
    - `delete pagos/{id}`;
    - el pedido con `pagado: increment(-monto)` y `ultimoPagoId: id`;
    - si existe `cajas/{recibidoPor}`, `enMano: increment(-monto)` y `ultimoPagoId: id`.

Reglas, al nivel de las funciones de ayuda:

```
function igualDinero(a, b) { return math.abs(a - b) < 0.001; }
function rutaPago(id) { return /databases/$(database)/documents/pagos/$(id); }
function rutaCaja(uid) { return /databases/$(database)/documents/cajas/$(uid); }
function pagadoAntes(ruta) { return exists(ruta) ? get(ruta).data.get('pagado', 0) : 0; }
function enManoAntes(ruta) { return exists(ruta) ? get(ruta).data.enMano : 0; }

function pagoValido(d) {
  return d.keys().hasOnly(['pedidoId', 'monto', 'forma', 'recibidoPor', 'fecha'])
    && d.pedidoId is string
    && d.monto is number && d.monto == d.monto && d.monto != 0
    && d.monto > -1000000000 && d.monto < 1000000000
    && d.forma in ['efectivo', 'transferencia']
    && d.recibidoPor == request.auth.uid
    && d.fecha == request.time;
}

// Lado del pedido: el pago {id} se refleja en pagado (crear: +monto; borrar: -monto).
// En create, pedidoId = request.resource.data.pedidoId; en delete, resource.data.pedidoId.
function pagoEnPedido(id, pedidoId, monto) {
  let ruta = /databases/$(database)/documents/pedidos/$(pedidoId);
  return getAfter(ruta).data.ultimoPagoId == id
    && igualDinero(getAfter(ruta).data.pagado - pagadoAntes(ruta), monto);
}
// Lado de la caja: lo mismo con enMano.
function pagoEnCaja(id, uid, monto) {
  return getAfter(rutaCaja(uid)).data.ultimoPagoId == id
    && igualDinero(getAfter(rutaCaja(uid)).data.enMano - enManoAntes(rutaCaja(uid)), monto);
}
```

Reglas de `pagos`:
- **read:** `esDueno() || (activo() && resource.data.recibidoPor == request.auth.uid)`.
- **create:** `pagoValido(d)`, `pagoEnPedido(id, d.pedidoId, d.monto)` y además una de dos:
  - `esDueno()`;
  - `esEmpleado() && d.monto > 0 && pagoEnCaja(id, request.auth.uid, d.monto)`.
- **update:** `false`.
- **delete:** `esDueno()`, `pagoEnPedido(id, resource.data.pedidoId, -resource.data.monto)` y además `!exists(rutaCaja(resource.data.recibidoPor)) || pagoEnCaja(id, resource.data.recibidoPor, -resource.data.monto)`.

Reglas del pedido:
- **Lado del pedido, `pagadoRegistrado(p)`.** Basta con una de tres:
  - `pagado` y `ultimoPagoId` no cambian;
  - se crea un pago nuevo: `ultimoPagoId` cambia, `!exists(pago)`, `getAfter(pago).pedidoId == p` y `igualDinero(delta, getAfter(pago).monto)`;
  - `esDueno()` borra un pago: `exists(pago)`, `!existsAfter(pago)`, `get(pago).pedidoId == p` e `igualDinero(delta, -get(pago).monto)`.
  - En los tres casos, `delta` = `pagado` nuevo − `pagado` anterior, con `get('pagado', 0)` en los dos lados.
- **create** acepta una de dos:
  - `get('pagado', 0) == 0` y `ultimoPagoId` nulo o ausente;
  - un pago creado en el lote: `!exists(pago)`, `getAfter(pago).pedidoId == p`, `getAfter(pago).monto > 0` e `igualDinero(pagado, getAfter(pago).monto)`.
- **update** agrega `&& pagadoRegistrado(p)`. La lista `soloCambia` del empleado suma `'pagado'` y `'ultimoPagoId'`.
- **delete:** `esDueno() && resource.data.get('pagado', 0) == 0`.
